# 群消息语义判断

判断群消息是否应该写入反馈文档时读取本文件。

## 视频消息

一条消息满足下面条件时，视为一个版本视频：

- 消息里有可下载的视频或文件资源。
- 发送者属于配置的项目 owner/版本视频发送者，通常是用户本人 `open_id`。
- 能从文件名、消息文字或发送日期推导出版本号。

策划、同事或其他成员发送的视频默认是参考视频，不要创建版本区块，也不要让它成为后续反馈挂载的“最近视频”。只有用户明确要求保存参考视频时，才另行设计参考素材区域。

版本号优先级：

1. 优先使用文件名或消息文字里的显式 `MMDDvN`，例如 `0616v2`。
2. 没有显式版本号时，用消息日期加当天递增序号推导 `MMDDvN`。
3. 如果用户后续修正版本号，更新状态和文档标题，不要创建重复版本。

视频识别到后要立即插入文档，即使还没有反馈。

## 正式策划反馈

满足任一条件时归入 `策划反馈`：

- 消息包含明确标签：`策划反馈`、`线下反馈`、`面聊反馈`、`制作会反馈`、`反馈整理`、`整理反馈`。
- 消息包含补充标签：`反馈补充`、`补充反馈`，并且是在延续上一条正式反馈编号时，也归入 `策划反馈`，继续按原编号顺序渲染。
- 发送者在配置的策划 `open_id` 列表内，并且文字明显是在给反馈。
- 发送者在配置的策划 `open_id` 列表内，消息包含图片并带有明确说明文字，例如位置标注、镜头/兵线/时间点要求；这类图片标注反馈即使没有写标签也要同步。
- 发送者在配置的策划 `open_id` 列表内，先发一条纯图片，紧跟下一条文字说明图片意图或修改要求时，把这两条消息合并为同一条 `策划反馈`。图片消息提供图片，文字消息提供反馈内容；文字消息本身不要再单独重复入库。
- 发送者在配置的策划 `open_id` 列表内，短句是在补充运动、速度、移速、节奏、时间点、画面位置、模型/建模、尺寸大小、出场早晚等明确要求，也应归入策划反馈，例如“boss速度比正常小兵移速快”“boss换另一个建模、再大一点、早出场一两秒”。
- 配置的用户本人发送了带标签的线下策划反馈整理。

同一条正式反馈消息里的图片也要接受，并放到对应视频下方。

没有被紧跟文字说明承接的纯图片、等待回复、约线下讨论、项目背景问答不要自动归入策划反馈。

## 反馈优先级

同一版本同时存在策划/同事反馈和配置用户本人发送的 `反馈整理` 或 `整理反馈` 时，以用户整理稿作为最终可见内容：

- 文档只渲染用户整理稿里的反馈条目和图片。
- 用户本人后续发送的 `反馈补充` 或 `补充反馈` 视为整理稿的延续，要接在整理稿后继续编号并显示。
- 同版本早先的策划/同事零散反馈仍可保留在本地状态里，便于追溯，但不要继续显示在文档正文。
- 如果 `反馈补充` 早于整理稿，且同版本后来出现整理稿，则优先以整理稿为准，早于整理稿的补充不再单独显示。
- 如果没有用户整理稿，才按策划反馈和同事反馈分别渲染。
- 用户整理稿默认归入 `策划反馈`；如果它带有 `制作会反馈`，则按制作会展示版本规则渲染。

## 同事反馈

消息满足下面任一条件时归入 `同事反馈`：

- `同事反馈`
- `同事补充反馈`
- 用户认可的其他等价团队短语
- 发送者在用户指定的可信同事反馈来源 `open_id` 列表内，并且消息是明确反馈，例如带多条编号、带反馈图片且文字包含反馈关键词、或用户已经确认这类消息应同步。

普通同事讨论不要当作 `同事反馈`。即使发送者在可信来源列表内，也要继续忽略普通问答、短确认和纯聊天。
可信同事来源的无标签单句消息要更保守：没有多条编号、没有反馈图片时，不要只因为出现“反馈 / 问题”等词就写入文档。

同一条同事反馈消息里的图片也要接受，并放到对应视频下方。

## 应忽略的讨论

除非消息有明确反馈标签，否则忽略这些内容：

- 项目问题或实现讨论：`吗`、`么`、`怎么`、`是不是`、`是否`、`有没有`、`是吗`
- 判断提问时不要把“那么 / 这么 / 多么”里的“么”当成提问标记；优先用 `吗`、问号、`怎么`、`是不是`、`是否`、`有没有` 等更明确的标记。
- 确认和回应：`好的`、`收到`、`有的`、`可以`、`ok`、`嗯`
- 没有反馈内容的短片段
- 只是澄清前文的消息
- 用户说明属于上一版或内部会旧反馈的会议记录
- 但如果短句紧跟在策划纯图片之后，并且是在说明图片里的位置、空间预留、后续补做、先做某个效果等修改要求，则不要按“短片段”忽略，应与上一条图片合并为反馈。

不确定时保守处理：先不要写入文档，并说明规则可以继续调。

## 编号反馈

如果正式反馈消息里已经有编号，要拆成多条复选框，不要合并成一条。
编号识别要避开小数点，例如 `0.9`、`1.5` 这类数值不能被当成新的编号。
如果消息开头带 `@某人1.反馈内容`，说明 @ 提及后面紧贴了第 1 条编号；清洗文本时只删除 @ 提及本身，必须保留 `1.反馈内容`。

原消息示例：

```text
反馈整理：
1. 挤出来加速的小兵动画速率不要太快
2. 地编调整，画面中道路尽量是直的
3. 初始的偏移值加大
```

制作会反馈也按策划反馈处理；渲染时不要保留“制作会反馈”标签本身，只保留拆分后的反馈条目。同时把对应小版本标记为制作会展示版本：小版本标题显示为 `🚩 {version}（制作会）`，`本版定位` 使用橙色提示框，右侧反馈标题从 `策划反馈：` 改为 `制作会反馈：`。

补充反馈示例：

```text
反馈补充：
4. 国王在把两个小兵打掉之后停一下，等箭射到墙上再走
5. Boss再晚一些出来
```

渲染时不要保留“反馈补充”标签本身；应继续接在已有反馈后面，显示为第 4、5 条。

渲染为：

```xml
<checkbox done="false">1. 挤出来加速的小兵动画速率不要太快</checkbox>
<checkbox done="false">2. 地编调整，画面中道路尽量是直的</checkbox>
<checkbox done="false">3. 初始的偏移值加大</checkbox>
```

## 编辑后的消息

正式反馈记录用消息 ID 和内容 hash 跟踪。

当消息被编辑时：

- 重新解析反馈条目和图片 key。
- 更新已有反馈记录。
- 重新渲染对应版本的 `策划反馈` 或 `同事反馈` 区块。
- 重新渲染对应版本的反馈图片。
- 避免重复追加。
