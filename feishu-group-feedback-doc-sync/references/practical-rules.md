# 实战经验规则

搭建真实项目、调整分类规则、排查误判或漏同步时读取本文件。本文件沉淀实际使用中踩过的坑，优先级高于泛化猜测。

## 1. 视频先同步，反馈可以后补

- 群里出现项目 owner/用户本人发送的视频或视频文件后，先立刻创建对应版本区块。
- 策划、同事或其他成员发的视频默认是参考视频，不是版本视频；不要创建版本区块，也不要把后续反馈挂到这些参考视频上。
- 不要因为策划反馈还没出现，就延迟同步视频。
- 没有反馈时，反馈标题可以先空着；只在“本版定位”里写“等待后续反馈沉淀”这类说明。
- 不要根据群聊讨论自行总结“本版相比上一版改了什么”，除非用户明确要求。

## 2. 带图片的反馈必须连图片一起同步

- 正式反馈消息里如果带图片，图片和文字属于同一条反馈记录。
- 策划/设计人员发出的“图片 + 有意义说明文字”通常就是图片标注反馈，例如“让塔2建成的时候兵线在这个位置”；即使没有写“策划反馈”标签，也应归入策划反馈。
- 策划/设计人员单独补充的短句，如果是在说明速度、移速、节奏、时间点、画面位置、模型/建模、尺寸大小、出场早晚等明确要求，也要同步为策划反馈，例如“boss速度比正常小兵移速快”“boss换另一个建模、再大一点、早出场一两秒”。
- 纯图片、等待消息、约线下讨论、普通问答仍然不要自动归入反馈。
- 不要把“那么一两秒”里的“么”当成疑问词，否则会漏掉“早出场那么一两秒”这类正常反馈。
- 处理时必须从 IM 下载图片，上传到飞书文档，并放在对应版本视频下方。
- 图片顺序按消息中的出现顺序或消息顺序排列。
- 如果反馈消息被编辑，重新解析文字和图片 key；原有图片不要重复追加，应该按最新记录重新渲染。
- 不要只把反馈文字写进文档而漏掉图片。这个是高优先级验收项。

## 3. 正式反馈和普通沟通要严格区分

- 策划提出问题、追问项目情况、确认理解、和用户来回沟通，都不等于正式策划反馈。
- 用户回答过的问题不应被整理成策划反馈。
- 同事在补充旧版本或内部会的反馈时，不要自动归到当前版本；需要按用户说明归属到对应旧版本，或暂不写入。
- “有的”“好的”“收到”“可以”“ok”这类短回复永远不要单独作为反馈。
- 不确定时宁可不写入文档，并在日志或总结里提示需要用户确认规则。

## 4. 只有明确反馈才进入文档

- 策划反馈来源通常是：配置的策划人员发出的明确反馈，或用户本人整理的“反馈整理 / 策划反馈 / 线下反馈 / 面聊反馈 / 制作会反馈”。
- 如果同一版本里同时存在策划/同事反馈和用户本人发送的“反馈整理 / 整理反馈”，文档最终显示以用户整理稿为准；隐藏同版本零散策划/同事反馈及其图片。用户本人后续发送的“反馈补充 / 补充反馈”要作为整理稿延续继续显示；没有用户整理稿时，才展示策划/同事反馈。
- 用户或策划后续发送“反馈补充 / 补充反馈”时，应按同一版本的正式策划反馈继续追加，不要因为不是“反馈整理”就漏掉；渲染时去掉标签，只保留条目。
- “制作会反馈”本质上是制作会沉淀出来的策划/设计反馈，也归入 `策划反馈`，不要当成普通会议讨论或同事反馈。
- 收到“制作会反馈”后，需要把对应版本整体改成制作会展示版本：标题加 `🚩` 和 `（制作会）`，本版定位框改为橙色并写明“本版为制作会展示版本”，原 `策划反馈：` 标题改为 `制作会反馈：`。
- 同事反馈通常必须有明确标签，例如“同事反馈”“同事补充反馈”。
- 如果用户明确指定某位同事的反馈应算作同事反馈，把该成员 `open_id` 加入可信同事反馈来源；该成员发出的多条编号反馈、带图片且有反馈关键词的消息，可以归入 `同事反馈`，即使没有写“同事反馈”标签。
- 可信同事反馈来源仍然要过滤普通问答、实现讨论、短确认和纯补充说明，不要因为是白名单成员就把所有消息都写入文档。
- 用户已经明确说“这不是反馈”“这是正常讨论”“这是上一版反馈”时，必须按用户判断修正规则。
- 不要为了让文档看起来更满而把讨论内容塞进去。

## 5. 编号反馈要拆开，不要合并

- 如果用户或策划发出的反馈本身带 `1.`、`2.`、`3.` 编号，要拆成多条复选框。
- 如果补充反馈从 `4.`、`5.` 开始编号，也要拆成多条复选框，并接在已有 1-3 后面。
- 如果消息格式是 `@某人1.反馈内容`，不要把 `@某人1.反馈内容` 整段当成 @ 提及删除；应只去掉 @ 提及，保留 `1.反馈内容`，否则会漏掉第一条反馈。
- 拆编号时不要把小数误拆成编号，例如 `缩到0.9` 必须保持在同一条反馈里，不能拆成 `缩到` 和 `9`。
- 不要把整段编号反馈塞进一个复选框。
- 如果一条消息里混合了说明文字和编号条目，优先提取编号条目；必要时保留说明为短前言。

## 6. 编辑过的反馈要更新原记录

- 飞书消息被重新编辑后，应该更新已有反馈记录，而不是新增一份重复反馈。
- 用消息 ID、内容 hash、图片 key 跟踪反馈记录。
- 所有正式反馈都走“反馈记录 -> 重新渲染文字和图片”的路径，包括无图片的文本反馈；不要保留直接追加 checkbox 的旁路，否则后续带图反馈或重排时容易漏内容或残留错误项。
- 重新编辑后如果新增图片，图片也要补进对应版本视频下方。
- 重新编辑后如果删除图片，文档里的对应旧图片也要随记录重新渲染，避免残留。

## 7. 版本号和日期归属要允许纠正

- 用户发现版本号写错时，例如把 `0616v1` 误写成 `0615v2`，要修改原版本标题和状态记录，不要新建重复版本。
- 同一天多个小版本归到同一个日期下面。
- 新日期在上，旧日期在下；新阶段在旧阶段上方。
- 阶段切换后，新视频默认进入当前活跃阶段，不要继续落到旧阶段。

## 8. 文档展示规则

- 不显示消息链接、来源信息、发送人姓名。
- 视频用预览视口模式展示。
- 反馈图片放在视频下方，不要放到右侧反馈文字中间。
- `策划反馈`、`同事反馈` 保持为明显标题；即使污染目录也可以接受，因为目录可以折叠。
- 不同日期之间保持明显空行，方便快速定位最新日期。

## 9. 后台同步规则

- 自动同步不能每分钟弹窗打断用户操作。
- Windows 优先使用隐藏计划任务、`pythonw.exe` 和 `subprocess.CREATE_NO_WINDOW`。
- watcher 必须写 heartbeat 和日志，便于确认“还在不在”。
- 先手动同步成功，再安装 watcher。
- 再跑一次同步必须确认不会重复插入视频、反馈或图片。

## 10. 规则更新方式

- 用户指出误判时，先修正语义规则，再重跑受影响版本。
- 用户指出“策划视频其实是参考视频”时，删除误建的版本区块，把这些消息标记为参考视频，并重新把后续反馈挂回最近一个用户本人发送的版本视频。
- 用户指出“我发的反馈整理才是这一版最终反馈”时，给该记录标记用户整理优先级，并重渲染对应版本，显示用户整理稿以及整理稿之后的用户反馈补充。
- 用户指出漏图时，优先检查图片是否走了“正式反馈记录”路径。
- 用户指出排版不对时，优先检查是否仍按“阶段 -> 日期 -> 小版本 -> 视频/反馈”的层级生成。
- 新经验要沉淀回本文件，避免下一台电脑或下一位同事复现同样问题。
